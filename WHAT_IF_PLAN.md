# Design System and What-If Modes

## Summary

Add two distinct workflows:

- **Design System:** A live-only topology editor. Items, chute occupancy, metrics, analytics, and item controls are hidden. Node and conveyor changes update the real topology immediately. Selecting Done returns to the normal Live view.
- **What If:** An isolated, paused simulation forked from Live or from the currently displayed historical time. It displays items and metrics, permits topology and item edits, and never changes the live system.

The current simulation player can advance at real-time speed and into the future, but its ClickHouse polling can miss asynchronously persisted events. The real-time portion must therefore use a coordinated history-to-live handoff.

## Frontend Changes

- Add a persistent status strip with `LIVE`, `SIMULATION`, `WHAT IF`, or `WHAT IF SIMULATION`, each with a short hover explanation.
- Add a secondary `FUTURE` indicator when a simulation clock passes physical time and live intake freezes.
- Add header actions for **Design System**, **What If**, **Done**, and **Exit What If** when appropriate.
- Make Design System available only from Live.
- In Design System, load and subscribe only to locations and conveyors. Suppress item nodes, chute item counts, item subscriptions, item animation, HUD metrics, and the Live Interactions panel.
- Route Design System node and conveyor mutations directly to the live APIs. Refetch live graph data when Done is selected.
- Guard every node, conveyor, and item mutation outside Design System. From Live or Simulation, automatically create a what-if branch, show `Going into What If...`, wait until the branch is ready, and apply the pending mutation there.
- Allow explicit What If creation in addition to automatic branching on edit.
- Start every new what-if branch paused. Playback begins only when the user selects Play.
- When a live-derived branch is exited, destroy it and return to Live. When a historical branch is exited, destroy it and restore the paused source simulation at its fork time.

## Backend and API Changes

- Introduce simulation kinds `STANDARD`, `WHAT_IF_LIVE`, and `WHAT_IF_SIMULATION`. Keep them separate from lifecycle statuses such as `READY`, `PLAYING`, and `PAUSED`.
- Persist and expose the simulation kind, source simulation ID, fork timestamp, live handoff timestamp, and live-input state (`ACTIVE` or `FROZEN`).
- Add `POST /api/simulations/what-if` with an optional `sourceSimulationId`.
  - Without a source ID, fork atomically from current Live state.
  - With a source ID, pause the source simulation and fork from its exact server-side simulation clock.
- Keep the existing historical simulation creation API backward compatible, then regenerate the TypeScript API client from OpenAPI.
- Coordinate each fork under the live-state barrier: flush pending event history, establish a high-water timestamp, create the isolated baseline, and register subsequent live events without a gap.
- Classify event processing internally as external ingestion, live scheduled work, replay, or simulation-generated work. This is runtime metadata and must not change persisted event payload schemas.
- Replay all history through the fork timestamp, including observed item positions, so the branch starts from an accurate baseline.
- After the fork, accept external item creation, deletion, activation, destination, path, priority, rename, and property events, but discard external `ItemPositionChangedEvent` and `ItemPositionDeletedEvent` events in what-if branches.
- Continue processing position events generated by the branch's own movement scheduler.
- Merge persisted events through the handoff timestamp with directly queued live events after it. Deduplicate by event ID and preserve timestamp ordering.
- Permanently freeze live intake when the scenario first advances beyond physical time. Future progression then uses only branch-generated events.
- Ensure manual scenario mutations use the current virtual timestamp, invalidate routing and path state, and rebuild affected movement schedules through the existing reducers.
- Keep scenario mutations namespaced in simulation OrientDB and Redis state and out of live ClickHouse history.
- Keep the paused source historical simulation alive while its child what-if branch is active so it can be restored on exit.

## What-If Event Policy

At and before the fork timestamp, reconstruct the complete observed state, including item positions. After the fork:

- Accept new items and their initial positions.
- Accept item deletion, activation, deactivation, destination, path, priority, rename, and property changes.
- Ignore external PLC position changes and position deletions.
- Accept topology and item edits made by the user inside the isolated branch.
- Process all backend-generated movement and position events for the branch.
- Stop accepting new live events after the branch enters the future.

This lets the backend predict movement against the modified topology without PLC position observations forcing items back onto the real system's paths.

## Test Plan

- Add Testcontainers-backed integration tests for atomic live forks, historical forks, source isolation, cleanup, capacity failures, and virtual timestamps.
- Verify that the history-to-live handoff neither loses nor duplicates events around asynchronous ClickHouse flushing.
- Verify that what-if branches reject external position events while accepting other item events and processing internally generated movement.
- Verify that topology and item edits affect only the branch and continue to influence routing, movement, metrics, pause, resume, and fast-forward.
- Verify that crossing into the future freezes live intake and broadcasts the updated mode.
- Add frontend tests for all status labels and tooltips, Design System visibility, live topology CRUD, explicit and automatic what-if entry, pending mutation application, paused startup, and returning to Live or the source simulation.
- Run the focused simulation and event-processing integration tests, frontend build and lint, and Playwright checks for desktop and mobile layouts.

## Assumptions

- Design System edits production topology and is available only from Live.
- Existing authentication and demo-mode restrictions remain unchanged. Live Design System mutations remain blocked in demo mode.
- What-if branches cannot be promoted to Live and are discarded on exit.
- Item changes are treated like topology changes: attempts from Live or a standard simulation automatically create a branch first.
- A historical source simulation remains paused and receives heartbeats while its child branch is active.
- Entering the future is a one-way live-input cutoff for that branch.
